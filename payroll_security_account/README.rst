Glue between ``payroll_security`` and ``payroll_account``, installed
automatically when both are.

Confirming a payslip posts its journal entry. With the payroll roles of
``payroll_security``, the person who confirms is the Approver, and an
Approver does not need, and usually should not have, accounting rights.
This module keeps both true:

- confirming, cancelling and reversing a payslip check the payroll role
  (and the four-eyes rule) with the user's own rights first, and only
  then create, post or reverse the journal entry with ``sudo()``;
- ``sudo()`` keeps the real user, so the entry's author (``create_uid``)
  is the Approver who confirmed it, not the superuser;
- ``sudo()`` lifts access rights only: lock dates, balanced entries and
  every other accounting constraint still apply;
- changes to the accounts, analytic account and tax of a salary rule are
  tracked in its chatter, next to the formula changes
  ``payroll_security`` already tracks.

``payroll_account`` also makes ``hr.payslip.run.journal_id`` required,
defaulting to the company's first general journal -- nothing, for a
company with none, which turns into a raw database error the moment a
batch is created. A per-company "Salary journal" setting fixes that: it
wins over the stock default, batches and payslips fall back to the stock
behaviour when it is not set, and a company with neither gets a clear
message instead of the database error.

Configuration
=============

Nothing is required. Give the Approver level of Payroll to whoever
confirms payslips; no accounting group is needed for the journal entry
to be posted.

A Preparer still cannot confirm, and a confirmed payslip can only be
cancelled (its entry reversed) by an Approver. An entry dated in a
locked period is refused exactly as it would be for an accountant.

Optionally, set the salary journal in Payroll > Configuration > Settings
> Accounting > "Salary journal". Leave it empty to keep the stock
behaviour (the company's first general journal); if the company has no
general journal at all, creating a batch says so and names this same
path instead of failing with a database error. On install, a company
with exactly one general journal named "Salaries" or "Payroll" (or their
translation in an installed language) gets it proposed automatically;
with none or with more than one candidate, nobody guesses -- set it by
hand.
