Splits payroll access by duty instead of the two stock groups (Officer,
Manager).

The Payroll category on the user form becomes one selector with four
levels, each including the previous one:

+-------+---------------------------------------------+------------------------------+
| Level | Group                                       | Duty                         |
+=======+=============================================+==============================+
| 1     | ``payroll_security.group_payroll_reader``   | Reader (audit): reads        |
|       |                                             | payslips, batches and        |
|       |                                             | reports                      |
+-------+---------------------------------------------+------------------------------+
| 2     | ``payroll_security.group_payroll_preparer`` | Preparer: builds batches,    |
|       |                                             | loads inputs, computes       |
|       |                                             | payslips                     |
+-------+---------------------------------------------+------------------------------+
| 3     | ``payroll.group_payroll_user``              | Approver: confirms, refunds, |
|       |                                             | closes and reopens           |
+-------+---------------------------------------------+------------------------------+
| 4     | ``payroll.group_payroll_manager``           | Administrator: salary        |
|       |                                             | structures, rules and        |
|       |                                             | parameters                   |
+-------+---------------------------------------------+------------------------------+

An orthogonal add-on in Extra Rights,
``payroll_security.group_payroll_payment`` ("Payroll: payments"), reads
payroll and is meant for whoever issues the payment files. Nobody gets
it by implication.

The stock groups are re-used, not replaced: every third-party ACL and
menu that points at them keeps working.

Besides the roles, the module adds:

- record rules per operation (a Preparer only changes payslips and
  batches that are not confirmed yet) and the multi-company rules
  ``payroll`` lacks on batches and payslip lines;
- server-side checks on every state change, so a direct RPC call meets
  the same rule as the buttons;
- an optional four-eyes control, per company;
- a chatter on salary rules and structures that tracks every
  configuration change;
- a log of every change to an employee's bank account on the employee's
  own chatter.

Configuration
=============

Assign the level on the user form, Payroll selector. "Payroll: payments"
is a checkbox in Extra Rights and is never implied.

On install:

- Officer and Manager are renamed Approver and Administrator.
- Approver no longer implies Contracts / Administrator. Every user who
  was a payroll user at install time keeps it, as an explicit group
  (logged).
- The department rule of ``payroll`` is neutralised: scope is the
  company.
- The new-user template loses every payroll group and Contracts /
  Administrator.

Four eyes (off by default): Settings, Payroll, Controls, "Four eyes".
Per company: whoever computed a payslip cannot confirm it, nor close a
batch holding payslips they computed.

Usage
=====

+------------------------------------------------------+---------------+
| Action                                               | Minimum level |
+======================================================+===============+
| Read payslips, batches, lines                        | Reader        |
+------------------------------------------------------+---------------+
| Create/edit draft payslips and open batches,         | Preparer      |
| compute, generate                                    |               |
+------------------------------------------------------+---------------+
| Cancel or reset an unconfirmed payslip               | Preparer      |
+------------------------------------------------------+---------------+
| Confirm, refund, cancel/reset a confirmed payslip    | Approver      |
+------------------------------------------------------+---------------+
| Close or reopen a batch                              | Approver      |
+------------------------------------------------------+---------------+
| Edit structures, rules, categories, registers, rule  | Administrator |
| inputs                                               |               |
+------------------------------------------------------+---------------+

Every check is made in Python as well as on the buttons, so a direct RPC
call (``write({'state': 'done'})``, the change-state wizard) meets the
same rule.

Salary rules and structures carry a chatter: formula, condition,
amounts, category, ``active`` and the rule list of a structure are
tracked.

Every change to an employee's bank account (created, number, bank,
holder, archived, deleted, and Odoo's own "trusted for payments" flag
where ``account`` is installed) is also logged on the **employee's**
chatter, with the author and the number masked but for its last four
digits. Odoo keeps logging it on the work contact as well. Who may trust
an account is still decided by Odoo alone
(``account.group_validate_bank_account``): no payroll level includes it.

Known issues / Roadmap
======================

- Scope is the company. A narrower scope (by department, as the stock
  Officer rule attempted) is not implemented.
- The employee portal (an employee reading their own payslips) is out of
  scope.
- Sibling modules that add models (``payroll_rule_time_parameter``,
  ``payroll_contract_advantages``) keep their own access rules, written
  for the two stock groups: the Reader and the Preparer get no access to
  them from this module.
- On uninstall the stock group names come back in English; the other
  languages follow the next time ``payroll`` is upgraded.
- The Reader reads employees through an access rule of its own, without
  being an HR Officer. Some fields of the employee form are reserved to
  HR Officers, so upgrading a module that extends that form (``payroll``
  itself, for one) logs an "Access Rights Inconsistency" warning for it.
  A Reader never opens that form from Payroll.
